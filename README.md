# Pantheon Spins

A social casino web app with original themed slot machines. **Play money only:**
Coins cannot be bought with real money and cannot be withdrawn.

| Path            | What                                                                   |
| --------------- | ---------------------------------------------------------------------- |
| `server/`       | Go 1.26 API (chi, pgx + sqlc, go-redis, golang-migrate, slog)          |
| `web/`          | React 18 + TypeScript + Vite, Tailwind, Zustand (PixiJS/Howler for games) |
| `game-configs/` | JSON slot configs shared by server and web                             |

## Run it

```bash
docker compose up --build
```

Open http://localhost:5173. The web container proxies `/api` to the server, so
cookies and CSRF behave exactly as in production. Migrations run when the
server starts.

If a host port is taken, override it, e.g. `SERVER_PORT=8088 docker compose up`
(see `.env.example` for all settings).

## Develop

The OpenAPI spec at `server/api/openapi.yaml` is the source of truth for the API.
After changing it or the SQL, regenerate:

```bash
docker compose run --rm gotools go generate ./...   # Go server stubs + models (oapi-codegen)
docker compose run --rm sqlc                        # Go DB code from db/queries (sqlc)
cd web && npm run gen:api                           # TypeScript API types (openapi-typescript)
```

Tests (no local Go needed; integration tests start Postgres and Redis with testcontainers):

```bash
docker compose run --rm gotools go test -race ./...   # all Go tests
docker compose run --rm gotools go test -short ./...  # unit tests only
cd web && npm test                                    # Vitest
```

With Go installed locally, the same commands work from `server/` directly.

## Server layout

- `cmd/api` – HTTP server entrypoint
- `internal/api` – generated from the OpenAPI spec (do not edit)
- `internal/db` – generated by sqlc from `db/queries` (do not edit)
- `internal/auth` – registration, login, argon2id, Redis sessions, password reset, Google OAuth
- `internal/wallet` – every balance change, inside a transaction that holds the wallet row lock
- `internal/games` – `SlotGame` interface, registry, crypto RNG (evaluators and games come next)
- `internal/bonus` – bonus state persistence (JSONB) and resumption
- `internal/play` – spin and bonus-action orchestration (one transaction each)
- `internal/httpapi` – handlers, CSRF, sessions, rate limiting, logging

## Rules the code enforces

- Outcomes are computed only on the server from `crypto/rand`. The client sends a game ID and a bet.
- A spin debits, credits, logs, and (if triggered) creates the bonus in one Postgres
  transaction under `SELECT … FOR UPDATE` on the wallet. Coins are `int64`.
- One unresolved bonus per user per game (unique partial index). Spinning that game is
  refused until it is resolved. Bonus actions carry the step number, so retries and
  double-clicks are rejected instead of applied twice.
